# Compiling Web Experience Instead of Generating Frontend Code

## Abstract

Small language models are attractive for private, local software development, but direct frontend generation asks them to solve product semantics, interaction design, visual composition, state wiring, accessibility and code production simultaneously. That problem is underconstrained and difficult to verify. The Polar Pyro Web Experience Engine changes the unit of neural work: Qwen3-0.6B selects a small set of typed UX symbols, while deterministic compilers, mathematical reasoners, owned renderers and browser oracles do the authoritative work.

The result is not “AI writes React.” It is a proof-carrying compilation pipeline from application semantics to an independently qualified user experience.

## Thesis

A useful part of web development is formalizable:

- routes, tasks and journeys are graphs;
- permissions and visibility form finite relations;
- interaction behavior forms state machines;
- components have typed props, slots and composition constraints;
- tokens form finite semantic vocabularies;
- responsive layout has containment and breakpoint obligations;
- accessibility, performance and dependency budgets are measurable;
- source generation can be deterministic.

The aesthetic residue is real but should not be smuggled into the correctness kernel. Polar Pyro captures ratified human judgment as versioned design languages and precedent recipes, then verifies actual rendered behavior separately.

## Separation of authority

Qwen proposes `UXBinding`. SAE or DEMIURGE supplies application truth. The UX compiler closes roles, routes, tasks and journeys. Euclid-Ω proves the mathematical obligations within its supported domain. The component solver chooses only audited components. The renderer materializes only frozen templates and canonical data. Browser oracles test the running result. LOOM composes repository-scale changes. Git and certificates bind evidence to the exact source candidate.

No participant can certify its own unsupported claim:

- the proposer cannot author its oracle;
- the renderer cannot claim browser correctness;
- a component library cannot claim correct product wiring;
- an MCP server cannot grant itself effects;
- a visually attractive screenshot cannot prove persistence, authorization or recovery.

## Why component libraries are inputs, not the architecture

Open-source component ecosystems provide enormous leverage, but mixing them directly creates style drift, dependency sprawl and inconsistent accessibility. The engine ingests providers into a curated capability registry. Each admitted component has a stable identity, source/license provenance, allowed slots, variants, accessibility behavior and compatible design languages. A project chooses one coherent lane; the registry supplies alternatives without exposing arbitrary package selection to the model.

## Verification contract

The plugin uses three-valued external receipts:

- `PASS`: the stated bounded claim has live evidence;
- `FAIL`: evidence contradicts the claim or a closed invariant was violated;
- `NO_RESULT`: a required backend, proof or measurement was unavailable.

Compilation `PASS` is intentionally narrow. A release certificate additionally requires mathematical obligations, source reproducibility, application seam tests, browser journeys, accessibility, responsive behavior, security, performance and mutation adequacy.

## Long-horizon substrate

Git is not a convenience layer. It is the transaction algebra of the forge. Each attempt has a frozen base, isolated worktree, candidate commit, diff, oracle evidence and promotion certificate. Concurrent movement of the canonical branch invalidates stale proof. This makes multi-day work restartable and enables different engines to repair or extend one another without losing ancestry or overwriting the source of truth.

TOAM records intent, residuals, evidence and promotion history. It does not replace Git for software truth. Semantic memory and holographic working memory remain rebuildable projections.

## Plugin and network model

The engine implements the Polar Pyro Plugin SDK manifest, grant and receipt boundary. Locally it runs as a confined native service. At the edge it may run behind an authenticated MCP/HTTP gateway. Wi-Fi access through N3IWF into a 5G core changes transport and tenant identity, not authorization: manifest digest, project/session binding, effect grants, evidence and oracle promotion remain mandatory.

## Evaluation

Success is measured by closed-binding accuracy, route/journey coverage, off-alphabet rejection, proof replay, renderer reproducibility, browser journey completion, accessibility defects, mutation score, rollback recovery, latency and final human judgment. The product-level exit gate is ten difficult applications—five stateless and five stateful—generated without product-source hand editing and published with complete receipts.

## North star

The target is a reusable experience compiler that lets a tiny local model direct a large deterministic software factory. Quality comes from structured semantics, curated design assets, mathematical closure, real browser evidence and accumulated precedents—not from asking the model to imitate a frontier coder one token at a time.
